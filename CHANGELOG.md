# Changelog

All notable changes for users of depcurfew. The project follows [semantic versioning](https://semver.org/): the policy file (`version: 1`), the command-line options, the exit codes and the JSON and SARIF output (`schemaVersion: 1`) only change in a backward-incompatible way in a new major version.

## 1.4.0

### Composer

- depcurfew supports Composer (PHP packages from Packagist). `apply` writes the Composer 2.11 release-age delay into `composer.json` (`config.policy.cooldown.period`, in whole days rounded up, with the `composer:` exceptions of `cooldown.exclude` in `ignore`) and, with `installScripts.default: "deny"`, the plugins of `installScripts.allow` and `installScripts.deny` into `config.allow-plugins`. When it changes `config.policy` and `composer.lock` exists, it says to run `composer update --lock` (`lockfile-out-of-date`): Composer 2.11 hashes the policy into the lock. A delay that is already as long, written another way (`259200`, `"72 hours"`), stays. When `cooldown.exclude` drops a package, `apply` removes the `ignore` entries it wrote itself in the object form, marked by their reason; any other entry, including one it wrote earlier in the list form, which carries no mark, stays and gets a warning (`exclude-entry-outside-policy`) and a `config-drift` finding.
- `init` lists the Composer plugins of `composer.lock` to review, and says which ones `allow-plugins` already allows. `apply` refuses a `composer.json` with comments or trailing commas, which Composer cannot read (`cannot-edit`, with the line), and nothing is written.
- Policy package lists accept Composer packages with the prefix `composer:` (`"composer:monolog/monolog"`, `"composer:acme/*"`), with hints for a misspelled prefix and for a `vendor/name` written without one.
- New `doctor` rule `composer-config-weakens`: `composer.json` settings and CI `env` variables that turn Composer's cooldown, malware blocking, `allow-plugins`, `secure-http` or TLS off, such as `"policy": false`, `"allow-plugins": true` while the policy denies plugins, or `COMPOSER_NO_BLOCKING=1`.
- `doctor` reads `composer.lock` as Composer does. Packages from VCS, path, artifact or package repositories, and packages without an archive or with an archive without a type (which Composer clones), are checked against `sources` (`lockfile-forbidden-source`). Packages that `config.preferred-install` checks out from source give one error per entry, at its line in `composer.json` (and `init` notes them, `composer-source-checkouts`). While `sources.git` is `"deny"`, an archive from GitHub, GitLab, Bitbucket or Codeberg whose VCS source is on another host (compared as URLs compare hosts, `www.github.com` as `github.com`, also for VCS repositories in `composer.json`) gets a warning, and while `sources` denies a kind of source, archives from a host depcurfew does not recognize give one warning per host that names the declared Composer repositories (WPackagist archives on `downloads.wordpress.org` are recognized). Plugins (types `composer-plugin` and `composer-installer`, in any case) that `allow-plugins` lets run are checked against `installScripts` (`lockfile-install-scripts`), including every plugin of a `composer.lock` from before `allow-plugins` existed, which Composer 2.2 to 2.9 load without asking. `allow-plugins` keys match as in Composer (any case, `*` also covers `/`). A lock written by a Composer older than 2.11, which ignores the delay, is reported by `manager-version-too-old`. `doctor --osv` also checks every release locked in `composer.lock`, including releases from an unrecognized archive host and releases Composer checks out from source.
- Dependabot `composer` entries and Renovate (the `packagist` datasource, the `composer` manager and the `php` category) get the delay and the Composer exceptions. `doctor` compares them with Composer's delay, and notes that Dependabot counts from the release time the package author sets, while Composer counts from when Packagist received the version, and that Dependabot's `composer.lock` changes fail `composer validate` after `apply` (it hashes the lock with Composer 2.10.3; run `composer update --lock` on its branch).
- `depcurfew check composer:vendor/name[:constraint]` and `check_packages` of `depcurfew mcp` look Composer packages up on Packagist. They pick the version Composer would install, with `minimum-stability` and `prefer-stable` of the root `composer.json`, and report a release younger than `cooldown.minimum` (counted from Packagist's `published-time`, as Composer 2.11 does), unknown names, constraints no release matches, branches and `@dev`, plugins the policy does not allow, and abandoned packages. A root `composer.json` that declares other repositories or turns packagist.org off makes them `unverified`, with the file and line, and they are not sent to Packagist then. Packagist answers over 16 MiB, with more than 10,000 versions or with a version longer than 255 characters are `unverified` too.
- The Claude Code hook checks `composer require` (also `r` and Composer's short command names), `composer global require`, `composer create-project` and `composer update` of named packages, including `php composer.phar …`, `--working-dir` and options before the command name, as Composer reads them; a script of `composer.json` counts as a command, like `npm run`, but a command word that is a Composer command without `scripts-aliases` (which Composer before 2.7 ignores) is checked as that command. It asks when a command turns off Composer's protections (`--no-blocking`, `--no-cooldown`, `COMPOSER_NO_BLOCKING`, `COMPOSER_POLICY=0`, `COMPOSER_POLICY_MALWARE_BLOCK=0`, a shorter `COMPOSER_POLICY_COOLDOWN_PERIOD`) or changes Composer's configuration or repositories next to another Composer command, when the command sets `COMPOSER` or `COMPOSER_HOME`, for `composer global update` of a package, and when the root `composer.json` declares other repositories.
- A `composer.json` in a parent directory is read as Composer reads it: Composer uses it only in a terminal after asking, or with `use-parent-dir: true`, so `check` and the hook keep its repositories but read the command word also without its scripts and check versions also at stability `stable`, and the stricter answer counts. A root `composer.json` depcurfew does not read (over 1 MiB, or not a regular file) leaves Composer packages unverified, and their names are not sent to Packagist.
- `--osv` covers Composer packages as the Packagist ecosystem (OSV.dev matches `v`-prefixed versions, so they are sent as `composer.lock` writes them), and `explain_policy` names the Packagist URL in `lookups.composerRepository`.

### Known malicious versions (OSV.dev)

- New opt-in `--osv` for `depcurfew check`, the Claude Code hook (`check --hook claude-code --osv`) and `depcurfew mcp --osv`: the version an install would pick is looked up in OSV.dev, in one batch query per command, and a version with an OpenSSF malicious-packages record (`MAL-…`) is an error (`known-malicious`) that names and links the record. The hook denies it and tells Claude to choose another package or version.
- New `depcurfew doctor --osv` and doctor rule `known-malicious`: every locked package version in npm, pnpm, Yarn, Bun and Deno lockfiles, `uv.lock`, `poetry.lock`, `pdm.lock`, `Pipfile.lock`, `pylock.toml`, pinned requirements and `composer.lock` is checked in batch queries, with an error per package and lockfile at its line. New GitHub Action input `osv` (default `false`) runs the same check in CI.
- `doctor --osv` checks the version the package manager installs: the tarball of npm's `resolved` and pnpm's `resolution.tarball` (read from the URL path as the registry reads it, also with a query, a fragment or escapes, and relative pnpm tarballs) and Yarn's `resolution`; a registry tarball URL it cannot read gives a warning. A lockfile entry whose name or version says otherwise gets a warning, and so does a registry entry of a lockfile without an exact version.
- If OSV.dev cannot be reached, or its answer has malformed record ids or an implausible number of records, nothing passes silently: `check` reports the package as unverified, the hook asks, and `doctor` gives a warning per lockfile. No text of an answer from a registry, Packagist or OSV.dev reaches the messages, also for a redirect to something that is not a URL or an answer that is not JSON.
- Without `--osv` nothing is sent to OSV.dev. With it, package names, ecosystems and versions go to `api.osv.dev`, private packages included. It catches only reported malware; the README section "Known malicious versions (OSV)" says what it does not cover.
- `explain_policy` of `depcurfew mcp` shows the OSV endpoint in `lookups.osv`; the library exports `runDoctorWithOsv` and `queryOsv`.

### Install scripts of well-known packages

- `depcurfew init` writes esbuild, fsevents and lefthook from the lockfile into `installScripts.deny` (unless the package manager's own allow-list already lets them run: then it lists them for review), with a note per package on why and what changes (`install-script-denied`, `install-script-project-task`), and lists the other packages with install scripts to review (`install-scripts-to-review`, `install-scripts-not-recorded`).
- For lefthook, whose install script only installs the git hooks, `init` and `doctor` tell you to run `lefthook install` once after each clone, as lefthook documents. The hints for these packages are given only for the package from the registry under its own name; from another source it is listed for review like any other.
- `doctor` gives esbuild, fsevents and lefthook findings of `lockfile-install-scripts` their own fix, and warns when esbuild is in `installScripts.deny` while npm leaves optional dependencies out (`omit=optional`, `--omit=optional`, `--no-optional`, `NPM_CONFIG_OMIT=optional`), because esbuild then has no binary. `apply` warns about the same case with the new code `deny-needs-optional-dependencies`, and `explain --json` shows it per install command as `optionalDependencies` (`omitted` or `kept`) in `project.jobs[].commands[]` and `project.dockerfiles[].stages[].commands[]`.

### Corepack on Node.js 25

- New `doctor` rule `corepack-unavailable` (warning), which respects the order of commands within one line: `packageManager` or `devEngines.packageManager` pins Yarn or npm, but a declared Node.js is 25 or later, which no longer comes with Corepack, so the pin has no effect there. The fix says how to install it (`npm install -g corepack`, then `corepack enable`). pnpm pins, a `yarnPath` in `.yarnrc.yml` that points at a Yarn release committed in the repository, and CI jobs or Dockerfile stages that install Corepack first are not reported. `explain --json` gives the line of that command as `corepack` in `project.jobs[]` and `project.dockerfiles[].stages[]`.

### Update bots and GitHub Actions

- `apply` gives the GitHub Actions that your workflows run the same release-age delay as your packages: it writes `default-days` into Dependabot's existing `github-actions` entries. Renovate's top-level `minimumReleaseAge`, which `apply` already writes, covers its `github-actions` manager.
- `doctor` (`bot-cooldown-mismatch`) checks that each bot waits at least `cooldown.minimum` before proposing a new action version, and `broad-exclusion` reports a Renovate rule that turns that delay off. The README says why the delay protects actions less than packages: their date comes from git, which the author sets.
- Renovate `packageRules` with `matchManagers` or `matchCategories` (for example `{"matchManagers": ["npm"], "minimumReleaseAge": "1 hour"}`) are now read. They give `bot-rule-shortens-delay` in `apply` and `bot-cooldown-mismatch` or `broad-exclusion` in `doctor`. A single string instead of a list is read as Renovate reads it, and a rule whose glob depcurfew cannot read (braces, character classes, `?`, extglobs) gets a `doctor` note when it may shorten the delay. For the actions, a rule with `matchFileNames` that covers every workflow file, or `matchDepTypes: ["action"]`, counts as covering them.
- A `.github/dependabot.yml` with YAML aliases gets a `bot-cooldown-mismatch` note at the alias, `apply` warns (`bot-config-unreadable`) and `init` notes it: Dependabot does not read aliases. `doctor` reports every Renovate rule that gives some update types a shorter delay, not only the shortest, and a rule with a matcher depcurfew does not evaluate (`matchBaseBranches`, `matchJsonata`, …) gets a note when it sets a shorter delay. `explain` shows the bot delay `apply` writes, rounded up to the bot's unit. `broad-exclusion` reports `"*/*"` in a Dependabot `composer` entry. Its numbers are read as Dependabot's YAML library reads them (`default-days: 010` is 8 days).

### Documentation site

- The documentation is also a website, https://depcurfew.github.io, built by `npm run site` from the README, the knowledge base and `schema.json`, so it says what the README says. It serves the policy schema at `schema.json` and at the stable address `schema/v1.json`, and has the depcurfew icon.
- Start pages for JavaScript (npm, pnpm, Yarn, Bun, Deno), Python (uv, pip, Poetry, PDM, Pipenv), PHP (Composer) and the update bots, each with the five-minute start, the settings depcurfew writes and the matching `doctor` rules. Every `doctor` rule, every `apply` and `init` code, the Claude Code hook, the MCP server and the GitHub Action have their own pages with stable anchors, and every knowledge base value links to its official source.
- The site loads nothing from other hosts, needs no JavaScript and follows the system's light or dark mode. `site/org-repo/` holds the workflow for the repository depcurfew/depcurfew.github.io, which builds the site once a day from the latest release, with the Pages permissions limited to the deploy job; it is set up there after this release (`docs/RELEASING.md`).
- The site has a look in the colors of the icon: grouped sidebar navigation (a Menu button on phones), a start page with quick links and the supported tools, an "On this page" list on long pages, and levels shown as labeled pills, with no JavaScript and nothing loaded from other sites.
- It keeps the documentation of every earlier release from 1.1.0 on under `/<version>/` (for example `/1.3.0/`): that version's README, knowledge base, changes and schema, with a banner naming the version and a link to the current docs, and a Versions page lists them. `npm run site -- --versions` builds them from the git release tags.

### Fixes

- `doctor` finds the lines of minified lockfiles in linear time: a minified `package-lock.json` with 20,000 entries takes a fraction of a second instead of about 48 seconds.
- Fix texts name a GitHub Actions job by its line when its key is not a valid job id, instead of quoting the key. Workflow `env` and steps are read through YAML anchors and aliases, which GitHub Actions supports. A package in `installScripts.deny` with `false` in `allowScripts` is reported when the npm in use is too old to read that denial. The `apply` warnings from comparing allow-lists start with the tool name, and `doctor`'s Tools line names a package manager set up in CI for the projects (`setUpInCi` in `--json`).
- The Claude Code hook asks when a command sets a package manager's variable in a way it cannot read as a value, for every package manager: `printf -v`, `read`, `mapfile`, `getopts`, `wait -p`, namerefs, `+=`, `for`, `${NAME:=…}`, arithmetic, `eval`, aliases, and cmd's `set /p` and `set /a`; a command that only names such a variable (`printenv PIP_INDEX_URL`) asks too. It also asks about a global change of Composer's configuration (`composer config --global`, `-g` or `--file`, and the same after `composer global`) even on its own, and about `poetry source add`/`remove` and `pdm config` next to an install. `${#NAME}` no longer makes a command unreadable.
- The Claude Code hook reads environment variables set in PowerShell on the `Env:` drive (`New-Item`, `Set-Item`, `Rename-Item`, `Copy-Item`, `Move-Item`, `Set-Content`) and through `[Environment]::SetEnvironmentVariable`, with parameters bound as PowerShell binds them (`-Name:COMPOSER`, `-N`, positions) and names with backtick escapes or quotes; it asks when such a command uses a name it cannot read (`"Env:$name"`, wildcards, splatting). A quoted `composer` command (`& 'composer' require …`) is read as the command.
- `init` and `apply` quote a Dependabot number as written and as read (`default-days: 016 …, which Dependabot reads as 14`).
- With `projects`, a package manager that the root shows only through a CI setup step (such as `pnpm/action-setup`) counts as set up for the projects when the root has no manifest of its registry, or when the CI jobs install with it at least once, every such install runs in a listed directory and no root Dockerfile installs with it. `doctor` no longer lists a root pnpm that does not exist and no longer warns about it on Dependabot entries of other projects, `apply` no longer writes its file (such as `pnpm-workspace.yaml`) in an npm root, and `explain` shows it under "Package managers set up in CI for projects" (`project.ciForProjects` in `--json`). `manager-version-too-old` still checks the version the step installs.
- `docs/knowledge.md` shows a value with a backtick inside (`docker.syntax`) in full instead of ending its code early.

### Upgrading from 1.3.0

- Run `depcurfew apply` again after the upgrade. In a repository with workflows, a `cooldown` and a Dependabot `github-actions` entry, 1.4.0 writes `default-days` into that entry; until then `config-drift` reports it. A longer `default-days` there is reported by `apply` (`cooldown-shortened`) and kept by `init`.
- In a repository with `composer.json`, `apply` now writes `config.policy` and `config.allow-plugins` there, the delay into Dependabot `composer` entries and a Renovate rule for `composer:` exceptions; until then `config-drift` reports them. After `apply`, run `composer update --lock` and commit `composer.lock`. The delay needs Composer 2.11.0 or later wherever `composer update` or `composer require` runs.
- A policy with `composer:` names needs depcurfew 1.4.0: 1.3.0 rejects the prefix (`invalid-policy` in `doctor` and the Action, `ask` in the hook).
- `doctor` checks more than 1.3.0 did, so a repository that passed can get new findings: `corepack-unavailable` for a Yarn or npm pin with Node.js 25 or later, the bot delay for GitHub Actions, Renovate rules with `matchManagers` or `matchCategories`, and in a Composer project `composer-config-weakens`, the sources and plugins of `composer.lock`, and a lock written by Composer before 2.11. With `doctor.failOn: "warning"`, which `init` writes, these warnings fail `doctor` and the Action.
- The `lockfile-install-scripts` findings for esbuild, fsevents and lefthook have a new `message` and `fix`; the rule id and level stay the same. `doctor --osv` warns about lockfile entries whose label differs from the tarball they install, and about registry entries without an exact version.
- The Claude Code hook now reads `composer` commands, which 1.3.0 let through without a check: it denies or asks where the policy says so.
- In a repository with `projects` and an npm root, 1.3.0 `apply` may have written a `pnpm-workspace.yaml` in the root because a CI job sets up pnpm for a project. 1.4.0 does not write it, but while the file exists it reads pnpm in the root from it, so `doctor` keeps listing a root pnpm (with `bot-cooldown-mismatch` warnings on the Dependabot entries) and `apply` keeps updating it. Delete the file by hand if nothing else uses it.
- The Action input `osv` needs the 1.4.0 Action: pin its commit SHA.

## 1.3.0

### An MCP server for other coding agents

- `depcurfew mcp` is a Model Context Protocol server over stdio, so that Claude Desktop, VS Code, Cursor and other agents can ask before they install a package. It has two tools: `check_packages` (the same checks and the same document as `depcurfew check --json`) and `explain_policy` (which `depcurfew.json` applies and what it allows). It speaks both the `initialize` handshake (protocol revisions 2024-11-05 to 2025-11-25) and the stateless revision 2026-07-28 with `server/discover`.
- The registry and the Python index come only from the server's own options and `.npmrc`, never from a tool call, so an agent cannot point the check at a registry that approves anything. A `directory` argument must stay inside the project. Fixes that would change `depcurfew.json` are not offered to the agent.
- It limits what a client can send (1 MiB per line, nesting depth 64, 4 calls at once), stops on a cancelled request, and ends quietly when stdin or stdout closes or on SIGINT and SIGTERM. The README has configurations for Claude Code (`claude mcp add`, `.mcp.json`), Claude Desktop and VS Code. The server only advises; the configuration `apply` writes is what enforces.

### Several projects in one repository

- The new policy field `projects` lists directories that are independent projects, such as `frontend` and `backend`, each with its own manifest and lockfile. `apply`, `doctor` and `explain` in the root handle every project with the root's policy, and configure the update bots once, from the root, with a delay that covers every project's package managers. `init` in a root without a manifest proposes the directories that have one.
- A listed directory that is missing, is not a directory, is reached through a symlink, has its own `depcurfew.json` or is a workspace package of the root is an error (new `apply` codes `project-not-found`, `project-not-a-directory`, `project-symlink`, `project-has-policy`, `project-in-workspace`, and the `doctor` rule `invalid-project`); nothing is written. A target that no directory uses gets `target-not-found`. The user policy cannot list projects. Policies without the field are unchanged.

### The npm and pip that come with Node.js and Python

- `doctor` now knows which npm each Node.js release brings and which pip each Python release brings. Node.js 22, still supported until 2027-04-30, comes with npm 10, which has no release-age delay and ignores settings it does not know without a word; Node.js 24 brings npm 11.10 or later only from 24.14.1. `manager-version-too-old` reports a CI job that installs with npm after setting up such a Node.js, a Dockerfile stage that runs `npm ci` or `pip install` on such an image, and the version files developers use, with the npm or pip version to install or the Node.js or Python release to move to.
- It reads Node.js versions from `.nvmrc`, `.node-version`, `engines.node` of a private package, the files setup-node's `node-version-file` names, the values of `${{ matrix.<key> }}`, and Dockerfiles (`Dockerfile`, `*.Dockerfile`, `Dockerfile.<name>`, `Containerfile`): `FROM node:<tag>` and `FROM python:<tag>` with `ARG` substitution and stages, and `npm install -g npm@…` or `pip install pip==…` before the install. A setup step only counts for the installs that follow it, before the next setup step. `explain` shows the jobs and Dockerfiles it read.
- New rule `runtime-end-of-life` (warning): a declared Node.js version that only allows release lines past their end of life, where they install packages or run code.

### doctor and the GitHub Action

- `doctor --strict` (also with `--user`) exits with 1 for warnings too; notes never fail. The JSON has a new field `strict`.
- New policy section `doctor` with `failOn: "error" | "warning"` (also in the user policy). `init` and `init --user` write `"warning"`, so new policies make `doctor` and the Action fail on warnings too; a policy without the section fails on errors only, as before (the new checks can still find new errors, see "Upgrading from 1.2.0"). `doctor --fail-on error|warning` overrides it (`--strict` is `--fail-on warning`), and so does the Action input `fail-on`, which is now empty by default and follows the policy. The JSON of `doctor` has the new fields `failOn` and `failOnFrom` (`option`, `policy` or `default`).
- The rule list says "not applicable" for a check that does not concern the repository (Python rules in a JavaScript project, bot rules without a bot), instead of "passed".
- Action: new input `fail-on: error | warning`; with `warning`, warnings fail the step and the "depcurfew doctor" check like errors. `fail-on-error` still works and is deprecated; `false` keeps the step from failing whatever `fail-on` says, and now every other value counts as on.
- The "depcurfew doctor" check shows the findings as annotations on their lines (at most 100, errors first), and a workflow that runs on both `push` and `pull_request` updates the entry of the same commit instead of adding a second one.

### Protecting the whole machine

- `init --user` keeps the longest release-age delay already set in the user files of the installed tools, as `init` does in a project.
- Yarn's version is read from more places without running it: a global install of `@yarnpkg/cli-dist`, Corepack's `lastKnownGood.json`, and a `yarnPath` in `~/.yarnrc.yml` that names `yarn-<version>.cjs`. Bun from its official installer still needs `--for`.
- Poetry and PDM on macOS: the file they read depends on the platformdirs version installed next to them, which depcurfew now reads; when it cannot, `apply --user` writes where the documentation says and warns with both paths (`user-file-uncertain`).

### Claude Code hook and installation

- The README says what the hook does before depcurfew is installed: with `onFailure: "block"` a missing `node_modules/depcurfew` blocks every shell command, including the install that would bring it. It shows a `SessionStart` hook that installs the locked copy first, a layout for repositories without `package.json` in the root, and what to do in cloud sessions or when already locked out.
- `init` warns when it finds Python tools that the default policy also blocks building packages from source, so a package without wheels stops installing; run `doctor` before `apply`.
- The README recommends `--save-exact` and says what depcurfew does not do: it has no malware database, so use it together with a tool that blocks known malware.

### Fixes from the review before the release

- `apply` now considers every npm the repository runs: the pinned one, the npm that CI jobs and Dockerfiles install, and the npm that the declared Node.js versions bring (in a repository with `projects`, also the root's `.nvmrc`, `.node-version` and `.tool-versions` for projects without their own). If one of them is npm 11.16 to 11.x and install scripts are denied, it writes `strict-allow-scripts=true` (warning `strict-allow-scripts-for-npm-in-use`; with npm 12 an unreviewed script then fails the install instead of being skipped with a warning). `doctor` counts script blocking as the files stand, so the version it recommends really blocks them.
- `npm install -g <another package>` in CI or a Dockerfile no longer counts as a project install (npm ignores the project `.npmrc` in global mode). pnpm, Yarn and Bun installs in CI jobs count for `runtime-end-of-life`. In a repository with `projects`, a root CI job that installs with `working-directory` in a project is checked with that project's settings.
- Workflows and Dockerfiles from a pull request can no longer crash or stall `doctor` and the Action: large matrices are capped with a notice, the command and Dockerfile readers run in linear time, and `ARG` values are limited in size. A here-document marker inside quotes no longer swallows the rest of a Dockerfile. Identical findings are reported once, and findings at one place that differ only in numbers are capped with a count.
- `apply` checks again, right before writing, that no directory on the way to a file was replaced by a symlink that leads out of the repository.
- The Claude Code hook takes its policy from the project (`CLAUDE_PROJECT_DIR`) when the working directory is inside it, so a `depcurfew.json` in a vendored repository or package folder cannot relax it. The MCP server's `directory` argument cannot relax it either. Warnings without a decision (a deprecated version) reach Claude as context, and registry text is quoted and marked as data, with invisible format characters shown escaped.
- Node.js before 18 (npm 8 or older, which runs every install script) is no longer taken for an npm that blocks scripts: depcurfew knows the npm of every Node.js release, and an npm it cannot tell counts as running scripts (`scripts-not-enforceable`, and `lockfile-install-scripts` reports the packages). A Dockerfile `COPY` source is resolved from the build context as Docker does, so `COPY frontend/../ .` belongs to the root. A project inherits each root Node.js version file (`.nvmrc`, `.node-version`, `.tool-versions`) that it lacks, and `explain` shows what a project takes from the root.
- `check_packages` works on every Node.js that `engines` allows (it used `AbortSignal.any`, which needs Node.js 18.17 or 20.3).
- With `--json`, a usage error (an unknown option, `check` without a package, `--json` with `--sarif`) is a JSON document with `errors` on stdout, exit code 2, and stderr stays empty. `explain --json` warnings have `level`, `location` and `fix`, and an invalid project makes `explain` exit with 1.
- `doctor --user` warns when a tool in `PATH` is too old for the user policy instead of reporting no problems. In a project, bot files of a listed project are a note (bots read their configuration only from the repository root), and a project without a Dependabot entry for its directory is a warning.
- The "depcurfew doctor" check no longer keeps annotations of an earlier run with different findings: it replaces that entry. A symlink loop in the repository no longer crashes the Action.
- The Claude Code hook and `depcurfew mcp` apply the project's `depcurfew.json` and a nearer one together (the stricter answer counts) also when the project is not a git repository; when the project root has no policy, the nearest one applies alone, as in 1.2.0.
- A hook event that is not a JSON object, or a Bash, PowerShell or Monitor call without a readable command, now blocks the call (exit code 2) instead of letting it through.
- `check`, the hook and `check_packages` read `.npmrc` where npm reads it, so a listed project's own `.npmrc` counts. An `.npmrc` elsewhere, or a registry in `.yarnrc.yml`, `bunfig.toml` or uv's files, that names another registry than the one depcurfew checked makes the packages it applies to `unverified` (the hook asks); the fix says to pass `--registry` or `--index` to the hook command, `depcurfew mcp` or `check` when you trust that registry.
- The hook reads installs hidden in a `trap`, an alias defined in the command, grouped `env -S` options, `sudo -s`, `. npm …`, an interpreter that runs a package manager's script (`node /usr/bin/npm`, `node .yarn/releases/yarn-*.cjs`, `python3 -m pip.__main__`), and commands after a here-document with CRLF line endings.
- The hook asks when the command itself weakens the policy, also for `npm ci`: a shorter release-age delay (`--min-release-age=0`, `--before`, `UV_EXCLUDE_NEWER`), install scripts turned on where the policy denies them (`--ignore-scripts=false`, `npm_config_ignore_scripts=false`, `bun add --trust`), or a configuration or `package.json` change before an install (`npm config set registry … && npm ci`, `npm pkg set …`). `config get`, `config list`, an equal or longer delay and `--ignore-scripts` pass.
- The hook checks each install with the policies of the directory it runs in: after `cd`, `pushd`/`popd`, `cd -`, PowerShell's `Set-Location`/`Push-Location`, cmd's `cd /d`, and with `npm --prefix`, `pnpm --dir`, `yarn --cwd`, `bun --cwd`, `uv --directory`/`--project`, `poetry -C`/`-P` or `pdm -p`, so `cd pkgs/strict && npm install x` meets `pkgs/strict/depcurfew.json` and that directory's `.npmrc`. A directory outside the project is checked against the project's policy only. When the hook cannot tell the directory (`cd "$DIR"`, a `cd` in a loop or function), it asks about installs that name packages.
- Notes of `check --json` and the MCP tools have a `level` (`note`), a `code`, a `location` and a `fix` when there is one, and the text output shows `note: … (code)` with a `fix:` line.
- `doctor` checks the npm that a CI job or Dockerfile installs (`npm install -g npm@X`, also ranges such as `npm@^11.10.0`) for the project it installs in; `npm@latest` and `npm@${VAR}` count as an npm that may run every install script, in `doctor` and `apply` alike. A place that installs only with `npm ci` no longer needs a release-age setting, and one that installs with `--ignore-scripts` or `npm_config_ignore_scripts=true` no longer needs script blocking. Fixes no longer suggest an npm that cannot run on that Node.js.
- `doctor` reads job containers (`container: node:20`), `cd <dir> &&` before an install, `lts/-1` in `.nvmrc`, and Poetry installed with `pipx install poetry==X`. A stage whose `node` or `python` image is pinned by digest only, or has a tag depcurfew does not know, is a note with a fix in `manager-version-too-old` too.
- `doctor` reports pip installs in CI jobs and in Dockerfile stages of the `python` image that run without the policy's release-age delay (no `PIP_UPLOADED_PRIOR_TO` in `env:`, `ENV` or on the command line and no `--uploaded-prior-to`) or with a shorter one (`python-config-ignored`). Root jobs that install in a project count for that project; jobs and stages that set `PIP_CONFIG_FILE`, run `pip config set` or write a `pip.conf` are not checked.
- `init` skips git submodules, and `apply` and `doctor` refuse them as projects (`project-is-repository`). `doctor frontend` and the Action's `directory: frontend` use the root policy when it lists the directory in `projects`.
- New `doctor` rule `lockfile-out-of-date` (warning): a `uv.lock` or `pdm.lock` locked with other settings than the project has now, for example after `apply` changed `exclude-newer`. `apply` warns about a Renovate `packageRules` entry with a shorter delay (`bot-rule-shortens-delay`) and about Yarn's `enableScripts: true` (`allow-all-replaced`).
- `config-drift` reports every changed place in a file, rules that did not run because the policy is invalid show as skipped, and a Renovate file depcurfew cannot read is a note instead of a passed check. Notes have a level, a code and a fix in JSON and start with `note` in the text; syntax errors and `depcurfew.json` problems point at their line and column; `doctor --user` shows user-file drift with its line and the expected value.
- `explain` shows, for each tool, what `installScripts` and `sources` mean before `apply`: the setting `apply` writes and its file, or why the tool cannot enforce it, with the same warning code and fix as `apply`. `explain --json` has them in `policy.installScripts`, `policy.sources` and per project.
- The hook also applies the working directory's policy to installs after `cd`, `pushd`, `env -C` or `--prefix`, so changing directory can only tighten the check; a `cd` to a missing directory or a file asks, and `cd -P` and `set -P` follow symlinks. It decodes `$'…'` as bash does, asks about command names built at run time inside `eval`, `sh -c` and `trap`, reads abbreviated `--no-` options of npm and pnpm (`--no-ign`), treats the directory of `find -execdir` and of an install in a `trap` before a `cd` as unknown, and reads PowerShell paths with `\`.
- The hook asks about packages that Poetry (`[[tool.poetry.source]]`), PDM (`[[tool.pdm.source]]`) or Pipenv (`[[source]]` in `Pipfile`) would take from another index, and about packages that `[tool.uv.sources]` pins to an explicit uv index. When such a setting applies and the checked registry has no such package or version, the install is unverified (the hook asks) instead of denied as a made-up name.
- `doctor` reports a syntax error in a package manager's or bot's configuration file also without a valid `depcurfew.json`, and says "needs a valid depcurfew.json" for the checks it skipped. `doctor --user` reports each place where a user file differs from the user policy. An invalid `depcurfew.json` shows its line in the text of `apply`, `check` and `explain`, the Action's own log lines start with their level, and notes of `apply --json` and `explain --json` have a level and a code.
- `depcurfew init --json` (also with `--user`) prints the file written, the projects and tools, and every warning and note with a code, level, location and fix; the text output gives each its level word, code and fix.
- The hook reads `env -S` strings the way GNU env does (including `-C` inside them), follows the bash directory stack exactly (`dirs -c`, `pushd -n`, `popd -n`, `+N`/`-N`, a `popd` on an empty stack), and asks about installs after `OLDPWD` or `DIRSTACK` may be set through a name the shell builds, after a `trap` on DEBUG, ERR, RETURN or a signal that changes directory, after `.` or `source` of a file, or after a function that changes directory. Sourcing a Python virtual environment's activation script (`source .venv/bin/activate`, `Scripts\Activate.ps1`) stays quiet when the environment holds `pyvenv.cfg` and nothing earlier in the command may have written the script (a redirection with `<>` or after `( … )` counts as writing). When two policies deny a release for its age, the fix names the longer wait. `PIPENV_PIPFILE` moves a Pipenv install to its Pipfile's directory, aliases ending in a blank expand the next word as in bash, and override messages name the policy file that sets the delay.
- `doctor` without a valid `depcurfew.json` reports a YAML file whose aliases expand without end, as it does with a policy, and an update-bot file depcurfew cannot read or parse gets a note instead of a claimed default delay. The `script-not-followed` note points at its line, the Action names the line of an invalid policy, `home-missing` names the `HOME` variable when it is not an absolute path, and the `.npmrc` of a workspace package, which npm does not read, no longer makes the hook and `check` ask when depcurfew matches the workspace exactly as npm does.
- Smaller fixes: configuration files are read only as regular files of at most 1 MiB, so a named pipe in place of `~/.npmrc` no longer hangs `check`, the hook or `mcp`; the hook no longer stalls on self-expanding aliases, on `workspaces` patterns that repeat `**` or on long `pushd` sequences, and reads hostile commands up to 1 MiB in linear time; `doctor` and the Action read a CI run step or Dockerfile `RUN` of any length in linear time (past 256 `cd` or 1024 variable assignments they say so in a `script-not-followed` note), and large PDM, uv and drift checks no longer take minutes; registry documents with more than 100,000 versions are not checked, and two policies share each lookup; usage errors print as `error: … (usage)` with a fix, and an unknown `--hook` or a `--registry` or `--index` that is not an http(s) URL is a usage error (exit code 2); fixes given to agents tell them to ask the user; PyPI yank reasons are quoted, and line separators and Hangul fillers are escaped; `apply`'s diff hides the `.npmrc` client `key`; `apply --user` without a home directory reports `home-missing`; `doctor --user` calls Yarn 1.x Yarn Classic; `doctor: {}` counts as the default; `depcurfew-outdated` also reads `.claude/depcurfew`; the Action names an `http://` `GITHUB_API_URL`; `apply` removes an empty `[installer]` table it created in `poetry.toml`.

### Compatibility

- depcurfew runs on Node.js 18.3.0 or later (it needed 22 before); CI runs every command on the oldest supported version. Node.js 18 and 20 no longer get security fixes from the Node.js project.
- With `FORCE_COLOR` and `NO_COLOR` both set, and on Node.js 18 before 18.17 for `check`, Node.js no longer prints its own warnings to stderr, which stays empty with `--json`.

### Upgrading from 1.2.0

- Run `depcurfew apply` again after the upgrade. 1.3.0 knows which npm each Node.js release brings and writes `strict-allow-scripts=true` where an npm 11.16 to 11.x runs and install scripts are denied; until then `doctor` reports `config-drift`, and `manager-version-too-old` for the places that run such an npm and that 1.2.0 did not know of, such as a setup-node 24 or 26 job.
- `doctor` checks more than 1.2.0 did, so a repository that passed can get new findings, which `apply` cannot clear: a CI job or Dockerfile stage that installs packages on Node.js 20 or 22, which come with npm 10, is `manager-version-too-old` (error). With the policy `init` writes, which denies install scripts, that holds for `npm ci` too, because npm 10 runs every dependency install script; install npm 11.16 or later in that job (`npm install -g npm@11.16.0`, which needs Node.js 20.17.0 or 22.9.0 or later) or move it to Node.js 24.14.1 or later. With a policy that sets only a release-age delay, only installs that resolve packages (`npm install`, not `npm ci`) are reported. Also, a `pip install` in CI or a Dockerfile without `PIP_UPLOADED_PRIOR_TO` is `python-config-ignored` (error), and a `uv.lock` or `pdm.lock` locked before `apply` changed the delay is `lockfile-out-of-date` (warning).
- The hook may ask where 1.2.0 allowed: when the install would use another registry than the one depcurfew checked, or when the command itself weakens the policy.
- Use the same depcurfew version everywhere: on developer machines, in the `npx` cache, in the Action (pinned by commit SHA) and in the hook (`node_modules/depcurfew` or `.claude/depcurfew`). 1.2.0 `apply` rewrites the managed block without the lines 1.3.0 adds, and 1.3.0 `doctor` then reports them again.
- A policy with the `doctor` section, which `init` now writes, or with `projects` needs depcurfew 1.3.0: 1.2.0 rejects it as an unknown field (`invalid-policy` in `doctor` and the Action, `ask` in the hook).

## 1.2.0

### Protecting the whole machine

- `depcurfew init --user` writes a user policy (`~/.config/depcurfew/depcurfew.json`, `%APPDATA%\depcurfew\depcurfew.json` on Windows).
- `depcurfew apply --user` writes it into the user-level configuration of the installed package managers (npm, pnpm, Yarn, Bun, Deno, uv, pip, Poetry and PDM), which protects every project that does not set those settings itself, and `npx`, `uvx` and global installs. Versions are read from the files next to each executable, never by running it; `--for tool@version` gives a version by hand, and a tool that stops every command on a value its version does not understand gets nothing until its version is known. pip gets its release-age delay this way, which a project cannot set.
- `depcurfew doctor --user` reports user files that do not match the user policy, values in them that weaken every project, and environment variables that move, skip or override them.
  - It also checks the places that beat the user file: command sections such as `[install]` in `pip.conf`, the `[pip]` table of `uv.toml`, and the `~/.npmrc` that pnpm 10 reads ahead of its `rc` file. A value counts as depcurfew's only when it is exactly what `apply --user` writes into its block.
  - It fails closed: an invalid user policy (`user-policy-invalid`) and a user file it cannot read, parse or edit (`user-config-unreadable`) are errors with exit code 1.
  - Environment variables are checked in every spelling and named as they are set. The default `~/.npmrc` that npm passes to `npx` and `npm run` is not reported, and values that may hold credentials are never printed. `--sarif` locates user files relative to `HOME` without revealing the home path.
- `apply --user` treats a key in a user file as `apply` treats the same key in a project file: hand-written exception lists and Python build lists are commented out even when the policy lists none, longer delays it shortens are reported (`cooldown-shortened`), and the warnings of project mode appear here too (scripts that cannot be blocked, forced source builds, sources a user file cannot hold, allow-list patterns, denials that live only in project files, Yarn 1).
  - With npm 11.10–11.14 it does not write `min-release-age` next to `before=` in `~/.npmrc`, where every npm command would fail; it warns instead.
  - It writes the files of all tools or none, refuses a missing home directory (`home-missing`), skips a tool that would read a relative `XDG_CONFIG_HOME` or `%APPDATA%` (`user-directory-relative`), names every file by its `~/` path, and warns about environment variables that would leave what it writes without effect (`environment-overrides`).
  - `--for` accepts versions as tools print them (`pip@26.1`) and warns when it names a tool that is not configured (`version-not-used`).
  - After `corepack enable`, pnpm and Yarn shims are no longer read as version 0.34.0; their version is unknown until `--for` gives it.
  - It turns off a switch in a user file that runs every install script (`dangerously-allow-all-scripts` in `~/.npmrc`, pnpm's `dangerously-allow-all-builds` in `rc` and `dangerouslyAllowAllBuilds` in `config.yaml`) when the user policy denies install scripts, as `apply` does in a project.
  - It warns (`user-setting-overridden`) when `~/.npmrc` overrides a setting it writes to pnpm 10's `rc`, and `doctor --user` reports that even before the first apply.
  - `init --user` refuses a missing home directory as `apply --user` does, and a file in the way of `~/.config/depcurfew` is an error with a fix instead of a crash. Run as root with `HOME` kept, `init` and `apply --user` give new files in the home directory to its owner.

### Policy

- `installScripts.deny` lists packages you reviewed that work without their install scripts, such as `fsevents`, which ships a prebuilt binary. `doctor` no longer reports them while the tool does not run their scripts, and `apply` records the denial where the tool has one (npm 11.16+, pnpm 10.1+ as `ignoredBuiltDependencies` and from 10.26 in `allowBuilds`, Yarn, Deno 2.6+), so the tool stops warning about them on every install. For Python packages `doctor` reports a tool that would still build one from source. Policies without it stay valid.
  - `apply` never changes an allow-list entry you wrote for a denied package, or a tool's own denial of an allowed one; it warns with `deny-conflicts-with-file`, and `doctor` reports the same entries.
  - `depcurfew check` and the Claude Code hook do not block denied packages; a denied Python package without wheels gets a warning that it cannot be installed while building is blocked.
  - An npm pattern in `allow` and a `pypi:` name in `deny` no longer clash; two patterns that can match the same name are rejected, with an example name.

### Messages

- `doctor` rule and `apply` warning `depcurfew-outdated`: the project installs a newer depcurfew than the one running (a global install or an old npx cache), which may not know what the project's version writes or checks. When the version is only pinned in `package-lock.json`, it says to run `npm ci` first.

### Settings that switch protection off

- `apply` and `doctor` treat a switch that allows every install script as on for every value the tool does not read as off: pnpm's `dangerouslyAllowAllBuilds: "false"` (a string), `yes` or `"true"`, `dangerously-allow-all-builds=1` in `.npmrc` (also in the project `.npmrc` with pnpm 10, which `doctor` now checks), npm's `dangerously-allow-all-scripts=1`, the same in `npm_config_*` variables, and Yarn's `enableScripts: 1`.
- YAML merge keys (`<<: *defaults`) in `pnpm-workspace.yaml` and pnpm's `config.yaml` are read as pnpm reads them, so a setting that arrives through one is no longer hidden; `apply` writes its value into the map itself, which wins over merged keys. `.yarnrc.yml` and `dependabot.yml` are read without merging, as those tools do.
- `doctor` reports an allow-list entry that lets a package of `installScripts.deny` run its scripts as an error, names a missing JSON setting by its path, lists every `.npmrc` line outside the block, and reports an `.npmrc` that is not a regular file instead of showing it as missing.

### What doctor checked

- `doctor` and `doctor --user` say below the result what they checked: the package managers and bots found, with the version they checked against, the files read, and every check in plain words with its result (passed, the problems it found, or skipped because it needs a policy that is missing). `--json` has the same in the new `checked` field.
- The GitHub Action prints the same in the log, adds a "What was checked" table to the job summary and, when there is nothing to report, a notice with the list of checks, so a clean run no longer looks like one that did nothing.
- The GitHub Action adds the check "depcurfew doctor" to the commit, shown next to the code scanning entry in the Checks tab of a pull request, with the result as its title ("No problems found (13 checks: 13 passed)") and the table of checks and findings. It needs `checks: write` in the job's permissions; without it, or with `check-run: false`, the step only says so in the log. On a pull request it goes on the head commit.

### Safety of output and files

- Diffs from `apply --dry-run` and `apply --json` show tokens and passwords (`_authToken`, `_auth`, `_password`, `user:password@` in URLs) as `<redacted>`; the files on disk are untouched.
- JSON and SARIF output escape C1 control and bidirectional characters, and the text diff of `apply --dry-run` shows control characters from files as text, also when piped.
- Files are read only when they are regular files and never past 1 MiB, whatever size the file system reports, so a FIFO or a file under `/proc` in place of a configuration file no longer makes depcurfew hang or run out of memory.
- Run as root (`sudo` with `HOME` kept), `apply` keeps the owner of each file it replaces.
- `depcurfew … | head` no longer ends with an EPIPE stack trace.

## 1.1.0

Everything below is new since 1.0.0. Upgrading needs no change to `depcurfew.json`.

### Guarding installs

- `depcurfew check <package...>` looks packages up in the npm registry or PyPI before you install them: names that do not exist or look like a popular package, versions younger than the delay, install scripts or builds from source the policy does not allow, yanked, deprecated or quarantined versions, and sources the policy denies. `--json`, `--dir`, `--registry` and `--index` are supported.
- `depcurfew check --hook claude-code` is a PreToolUse hook for Claude Code (the Bash, PowerShell and Monitor tools) that blocks install commands breaking the policy and asks when it cannot tell what a command installs. It is a safety net, not a sandbox.

### Python

- `apply`, `doctor`, `explain` and `check` support uv, pip, Poetry, PDM and Pipenv. Python packages are named with the `pypi:` prefix in the policy, and for Python `installScripts` covers packages built from source.
- After `apply` changes settings that a lockfile records (uv, PDM), lock again; `apply` and `doctor` say when.

### Messages and machine output

- `depcurfew apply --json` prints the changes with their diff, the warnings and the errors as one JSON document. Every warning and error has a code and says what to do.
- `doctor` reports an invalid `depcurfew.json` as a finding (`invalid-policy`); `check --json` and `explain --json` print JSON for it too.

### Behaviour changes and fixes

- `init` keeps the longest release-age delay the repository already sets, and `apply` warns before it would shorten one (`cooldown-shortened`).
- Without a directory, `apply`, `doctor` and `explain` use the nearest `depcurfew.json` up to the root of the repository, and only from a directory owned by the user that others cannot write to.
- `apply` writes every file or none, never makes a file it replaces readable by others, not even for a moment, keeps the line endings of the lines it does not change, and refuses files that are not UTF-8.
- `dependabot.yml`, `pnpm-workspace.yaml` and `.yarnrc.yml` with comments after the last entry are edited correctly; the result of every YAML, JSON and TOML edit is checked before anything is written.
- New `doctor` rule `python-config-ignored`, and more configuration that does nothing is found, among others `before=` and quoted keys in `.npmrc`, Yarn `npmScopes` age gates, pnpm `permissions.*.build`, broad Renovate rules and presets, and an out-of-date `pdm.lock`.
- Large lockfiles, `dependabot.yml`, `renovate.json` and SARIF output are processed much faster; YAML lockfiles over 16 MiB are reported instead of read.
- Windows: writes are tried again while another program holds a file, and the tests run on Windows in CI.

## 1.0.0

The first release.

- `depcurfew.json` holds one supply-chain policy: a release-age delay with exceptions (`cooldown`), an allow-list for install scripts (`installScripts`) and the dependency sources you allow (`sources`).
- `depcurfew init` writes the policy; `depcurfew apply` writes it into the configuration of npm, pnpm, Yarn (Berry), Bun, Deno, Renovate and Dependabot, keeping comments and formatting and marking what it manages; `--dry-run` prints a diff.
- `depcurfew doctor` reports configuration that silently does nothing and drift from the policy, as text, `--json` or `--sarif`.
- `depcurfew explain` shows what was detected and what the policy means for each tool.
- A GitHub Action runs `doctor` on every push and reports to code scanning.
- Node.js 22 or later; the library is ESM only. depcurfew does not use the network and has no telemetry.
